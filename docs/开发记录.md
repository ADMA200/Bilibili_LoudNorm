# Bilibili_LoudNorm — 开发记录

> **脚本名**：`B站响度归一`（`@name`）/ **`Bilibili_LoudNorm`**（`@name:en`）
> **产物**：`Bilibili_LoudNorm.user.js` · **当前版本 v1.0.0**
> **仓库**：https://github.com/ADMA200/Bilibili_LoudNorm

B 站网页版「响度归一」油猴脚本项目。目标是替代 greasyfork 587251《B站无损音量平衡》：
保留它「整片一个固定增益、播放中零干扰」的体验，换掉会干预播放、只采样开头的实现方式。

范围：普通投稿 `video/*` + 番剧/影视/电视剧/纪录片/国创/综艺 `bangumi/play/*`。不含课程、不含直播。

## S2.1 修复：单页内切视频 / 切分P 从「获取失败」到正常

**现象**（用户实测）：一打开就正常的那个视频之外，之后**不管是切分P 还是同页点开新视频，全部显示「获取失败」**。多标签页正常。

**根因**（`probe/raw/bls3_fail.json` 硬证据）：
`__INITIAL_STATE__` 与 `__playinfo__` 都是 **首屏那一份**，B 站 SPA 导航后**不会重新注入**。

| 观测点                     | SPA 跳转前     | SPA 跳转后（URL 已是 BV11b411L7mg） |
| ----------------------- | ----------- | --------------------------- |
| `location.pathname`     | `.../BV1GJ411x7h7/` | `.../BV11b411L7mg/`         |
| `__INITIAL_STATE__.bvid` | BV1GJ411x7h7 | **BV1GJ411x7h7（没变）**          |
| `__INITIAL_STATE__.cid`  | 137649199   | **137649199（上一个视频的）**        |
| `__playinfo__` 的 dash 时长 | 213s        | **213s（上一个视频的）**             |
| `<video>` 元素            | #1          | **#1（被复用，没换）**              |

于是脚本拿「旧 cid」配「新 bvid」去调 playurl，B 站直接回：

```
过期 cid 137649199 → {"code":-404,"message":"啥都木有","hasDash":false}
正确 cid  86380334 → {"code":0,"message":"OK","hasDash":true}
```

**双重危害**：
- 两视频时长差 > 2s → 过期判定触发 → 走接口 → **-404「获取失败」**
- 两视频时长差 < 2s → 过期判定漏掉 → **静默把上一个视频的响度算到新视频头上**（数字错但不报错，更阴）

**修复（四层，缺一不可）**：

1. **`state-reader.js` 加页面状态新鲜度校验** —— `__INITIAL_STATE__` 的 bvid 与 URL 不一致（或取不到 bvid）就**一律不采信**，cid 留空交给接口。这是地基。
2. **`playinfo.js` 加 `__playinfo__` 四重可信度判定** —— ①已采信过且 key 相同 → 复用；②SSR 状态新鲜 → 采信；③页面过期但对象**被换过**且时长吻合 → 采信（仍能吃 FastPath 红利）；④其余一律拒绝 → 回落接口。另外 `view` 接口按 bvid 缓存整份结果，切分P 零额外请求。
3. **`analyzer.js` 加「等播放器切流」** —— SPA 切视频时 URL 几乎立刻变，但播放器换流要晚 1–3 秒。这中间若照旧施加，就成了**把新视频的响度压到还在播的旧视频上**。现在时长达不上就先挂起（`waiting` 状态），等切流完成再算；宽限期 20s 兜底，避免播放器行为异常时永久失效。
4. **`lifecycle.js` 加路由变化检测** —— 只靠「video 元素被替换」会整个漏掉（实测点推荐视频后 45s 内元素都没换）。比对完整 href（含 `?p=`）。

另外 **缓存命名空间 `blv1` → `blv2`**：v1 时期写进去的条目可能是「用上一个视频的响度算出的增益」，属脏数据，不升版本会一直命中，修了也看不出效果。

**验证**：

| 套件                | 结果                                                                                                                                |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `s3-unit.mjs`     | **31/31** —— 含「事故全流程复刻」：先正常启动写入已采信记忆 → 模拟 SPA 跳转 → 断言拒绝过期 playinfo 并回落接口                                                          |
| `s3-nav-verify.mjs` | **17/17** —— 真实浏览器点推荐换视频两轮：key 的 cid 与 `view` 接口一致、状态判定过期、**playurl `-404` 零次**、**施加不早于宽限期**（旧实现约 1–3s 就压）、增益线性值换算回 dB 与显示值吻合 |
| `s2-unit.mjs`     | 101/101（回归）                                                                                                                       |
| `s2-verify.mjs`   | A/B/C/D 四场景（回归）                                                                                                                   |

**顺带发现**：多分P 视频的 `view.data.duration` 是**所有 P 的总时长**（实测 BV11b411L7mg = 1266s），单 P 真实时长在 `pages[p-1].duration`（182s）。用它当「等切流」的期望值会把判据整个搞反 —— 已写成断言钉死。

## S2.2：抽样时长不稳定（有时 6s+）→ 渐进式两阶段 + 旁路开关

**现象**（moxia实测反馈）：

> 「等待时长还好，但是抽样时长不太稳定，有时候很快，但有时得等 6s 以上。没有旁路开关，感受不明显，希望可以增加一个」

两件事：①**抽样时长抖动**（快则很快、慢则 6s 以上）；②**缺一个一键对比原声的旁路开关**。

### ① 根因不是「下载太多」，是「木桶效应」

原实现 **12 段全到齐才解码**，于是**最慢那一段决定整条链路何时可用**。慢段往往来自 CDN 冷连接、与播放器抢带宽、偶发重传 —— 恰恰是最不可控的部分。

用 CDP 限速（RTT 400ms / 200KB/s）精确复现，同一视频两种模式各跑 2–3 轮（`probe/s2-timing.mjs`，原始输出 `probe/raw/bls22_timing.json`）：

| 场景                | 不分批（S2.1 语义）        | 分批 + 够用即开工（S2.2）      | 改善                |
| ----------------- | ------------------- | --------------------- | ----------------- |
| 热网络 · 首次可用        | 699–741ms（中位 708）  | **212–516ms（中位 213）** | **−70%**          |
| 慢网络 · 首次可用        | 6152–6323ms（中位 6323） | **2846–3075ms（中位 3075）** | **−51%**          |
| 慢网络 · 最终稳定        | 6323ms              | 6562ms                | 持平（总工作量没变）        |

**慢网络那行的 6323ms 就是moxia说的「6s 以上」，复现成功。**

**三处结构性修改**：

| # | 改动           | 说明                                                                                                                                       |
| - | ------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | **够用即开工**    | 首批发出后**不等全到齐**，凑够 `firstBatchEagerAt=4` 段就把结果交出去先算，其余后台继续取。单元测试钉死 **`early 5ms / all 406ms`** —— 最慢段彻底离开关键路径                       |
| 2 | **分批 + 精修**  | 均匀 12 段里**等距**挑 6 段做首批（含首尾 → 覆盖仍是 0%–100%）先落位；剩余段后台补齐后重测。精修与初测差 ≥ `refineMinDeltaDb=0.5dB` 才重新落位，小差异不动（避免无意义抖动）              |
| 3 | **单段容错**     | 单段超时 15s → `segTimeoutMs=5s`，失败重试 1 次，仍失败就丢掉并记 warn；凑够 `minSegmentsToProceed=3` 就继续。原来任何一段抛错都让整次分析失败重来                                            |

另外把 init 与 sidx 两次 Range 改成**并行发**（区间互不重叠），省一个完整 RTT。

**代价（诚实记录）**：初测落在 4 段（≈19s 音频）时与 12 段精修结果增益差 0.37–0.91dB，超过 0.5dB 会重新落位一次 —— 用户可能在视频开头 1 秒内听到一次微调。HUD 用 `初测` / `已精修` 两个标记把这件事显性化。`progressive=false` 可退回原「等全批」语义，A/B 才是比同一件事。

### ② 旁路开关（A/B 对比原声）

关键设计：把**「想要施加的增益」与「实际施加的增益」拆成两个变量** ——

```js
desiredGainDb  // 归一流程算出的目标，旁路期间原样保留
bypass         // true 时 applyGain() 一律按 0dB 施加
```

于是**旁路 ≠ 停用**：分析照跑、结果照存、目标照记，**切回来是瞬时的**（不用重新等抽样）。三条入口：

| 入口              | 说明                                                                              |
| --------------- | ------------------------------------------------------------------------------- |
| 快捷键 `Shift+B`   | 默认键。B 站自身快捷键（`d` 弹幕 / `f` 全屏 / `m` 静音 / `w` 网页全屏）里没有 `b`，实测不冲突                    |
| 油猴菜单            | 「旁路开关（对比原声 Shift+B）」                                                            |
| 调试 API          | `__biliLoudness.setBypass(true)` / `toggleBypass()` / `isBypass()` / `getDesiredGainDb()` |

按下时 HUD 多一行 `旁路 听原声（归一 +X.XXdB 未施加）`，同时弹一个 1.4s 的小 toast（HUD 关着也有反馈，否则「按了没反应」A/B 做不下去）。

> ⚠️ 快捷键监听里**故意不调用 `preventDefault`**（构建守卫也禁止）—— 只是「顺便看一眼」按键，不拦页面行为。单元测试专门断言了这条。

### S2.2 新增的三个坑

### S3.2 新增的三个坑

1. **`root.style.cssText = ...` 在真机上直接崩** —— 主题变量原先是写到 `root.style` 上的，而 `root` 是 **ShadowRoot（DocumentFragment），根本没有 `style` 属性** → `TypeError: Cannot set properties of undefined (setting 'cssText')`。
   要命的是这个异常发生在 `boot()` 里，会把后面的 `Lifecycle.start()` 和 `exposeDebugApi()` **一起带走** ——

### S3.2.6 缓存淘汰语义修正（2026-10-03）→ v0.5.7

**起因**：moxia问「如果缓存超过 800 之后的逻辑是什么样的」。顺着 `store.js` 读了一遍，
发现三处**与名字对不上**的地方 —— 都不是崩溃型 bug，是「永远不报错、只是慢慢变差」的那种。

| # | 现象 | 后果 |
| -- | -- | -- |
| 1 | 只有 `set()` 续期，`get()` 命中**不**续期 | 淘汰实际按**最早写入**发生 → 是 **FIFO** 不是 LRU。常看的视频只要没重新分析过，照样被清 |
| 2 | TTL 过期只 `delRaw` 数据、**不动索引** | 索引里留下悬空条目，仍占 800 名额；要等它被 `shift` 到才顺手删（那时 `delRaw` 已是空操作） |
| 3 | `setRaw` 失败直接 `return false` | localStorage 配额满时**既不写也不淘汰** → 配额永远释放不出来，此后每条新测量都白跑；返回值在 `analyzer.js:470` 还被忽略，**全程无声** |

**改法**（全在 `src/store.js` 一个文件里）

- 新增 `bump(key)`：`get()` 命中时把该条挪到队尾。**已经在队尾就什么都不做** ——
  否则 analyzer 一轮里对同一个 key 连读几次，就要连写几次索引（800 条时约 40KB 的 JSON）。
- 新增 `dropFromIndex(fullKey)`：TTL 过期时数据与索引一起清；`remove()` 也改走它。
- 新增 `evictOldest(n)` + `writeIndex(idx)`：`set()` 写失败时先淘汰最旧 `ceil(上限 × 10%)` 条、
  再重试一次；成功 → `warn` 写明淘汰几条，仍失败 → `warn` 明说「不落盘」。索引写入失败也不再吞掉。

**验证（新套件）**：`probe/store-unit.mjs` **44/44** —— 沙箱里跑**真实的 `src/store.js`**
（假 localStorage，可设配额、可数索引写入次数）：

| 组 | 钉住什么 |
| -- | -- |
| 容量 | 写第 801 条后仍是 800（不存在中间态）、淘汰的一定是最旧那条、覆盖写不让索引虚长 |
| 真 LRU | 同一条最旧记录：**读一次之后再写第 801 条，被淘汰的不是它**（旧行为会淘汰它） |
| 索引写入 | 读队尾 key → 零写入；读非队尾 key → 恰好一次；未命中 → 零写入 |
| TTL | 过期后 `entries` 2 → 1（索引同步摘）、29 天内仍可用、`ttlDays=0` 视为永不过期 |
| 配额 | 配额不足时**仍写成功**且告警写明淘汰条数；彻底写不进时**如实返回 false** |
| 隔离 | `setSettings` 不占索引名额、`clear()` 不抹设置、`remove()` 数据与索引同删 |

**三个刻意的取舍**（写下来，免得以后当成 bug 改）：

1. **依然是「条数」上限，不是「字节」上限。** 800 条 × 每条约 300–500 B ≈ **0.3–0.4 MB**，
   而 localStorage 配额约 **5 MB** —— 条数永远先到，所以没做 §9 早期设想的「3MB 体积守卫」。
2. **仍按写入序淘汰，不做「访问频率」加权。** 一次 `get` 就提权，对「打开就看、看完就走」的用法已经够。
3. **配额满时宁可留悬空项，也不留孤儿数据。** `evictOldest` 是**先删数据、再写索引**：
   万一索引也写不进去，剩下的是「索引里有、数据没有」的悬空项（下次 `get` 直接返回 null，无害），
   而不是「数据有、索引没有」的孤儿（占着空间且永远淘汰不到）。

**回归全绿**：`s2-unit` 105/105 · `s3-unit` 31/31 · `s3-pgc-unit` 70/70 · `s3-panel-unit` 191/191 ·
`store-unit` 44/44 · **端到端** `s3-panel-verify` **85/85**（含场景 G 清除缓存不抹设置）·
`s2-verify` 全绿 —— **场景 C「同页重载 → `source=cache` 命中」**走的正是 `get()` 续期这条链，
改动后仍 **314ms 命中**，JS 异常 0 条。构建产物 **v0.5.7 / 212.4 KB / 15 模块 / 铁律守卫通过**。

> 只加 `--disable-gpu` 无效；**不需要放开外层沙箱**）。

### S2/S2.1 五个坑（都已修）

1. **sidx `first_offset` 的基准点是「sidx box 之后的第一个字节」，不是文件头** —— 漏掉会让每段整体前移 1482 字节，症状是「只有第 0 段能解码、其余全报 Unable to decode audio data」，响度只反映开头 5 秒（**本质是同一个字节偏移错误换了张皮**）
2. **多个 moof 拼成一个 Blob 后只能解出第一段** —— 必须逐段独立解码再拼 PCM
3. **BS.1770 多声道是能量求和不是平均** —— 按通道平均会让所有立体声素材系统性偏低 3.01dB。最阴的是当时的单元测试用了同一个错误假设做「解析预测」，所以自洽通过了（假阴性）
4. **`all:initial` 写在 cssText 末尾会把浮层推进文档流** —— 它是 shorthand、按书写顺序参与层叠，写最后就把前面的 `position:fixed` 一起重置成 `static`，HUD 掉到文档内 y≈2666px 处（视口才 450px），看起来就是「没有 HUD」。修复：`all:initial` 排第一 + 显式 `display:block` + `!important`；挂载改为「立即试 + 250ms 补试 + body 出现后从 `<html>` 迁进 `<body>`」；自检入口 `__biliLoudness.hudInfo()`
5. **`__INITIAL_STATE__` / `__playinfo__` 是首屏快照，SPA 导航后不更新** —— 直接采信就会「旧 cid 配新 bvid」→ playurl `-404 啥都木有`。详见上面 S2.1 一节；自检入口 `__biliLoudness.pageState()`

## S1 验证结论（三轮 CDP 自动化，全部通过）

S1 的目标是证&#x660E;**「只接管音频源、不改任何声音」这件事本身无害**。三轮验证：

| 验证       | 场景                         | 结果                                                                                            |
| -------- | -------------------------- | --------------------------------------------------------------------------------------------- |
| 单页       | `BV1GJ411x7h7`             | 接管 1204ms · `ctx=running` · **信号 RMS −16.89dBFS / 峰值 −1.88dBFS** · `video.volume` 未被动过 · 0 异常 |
| SPA 连播   | 同页点击 4 个不同视频               | **`<video>` 元素被复用（元素数恒为 1）**，切换 4 次只接管 1 次，每轮都有信号，0 异常                                        |
| **多标签页** | **4 个标签页各一视频，挨个播放、一次只播一个** | **卡暂停 0 次**：每轮 `currentTime` 均前进 3s（= 完全正常）· 4 页全部 `ctx=running` · 0 异常                       |

**「有没有声音」的判定方法**：只看 `ctx.state === 'running'` 不足以证明有声。脚本内置 `probeSignal()`，在 `masterGain` 上挂临时 `AnalyserNode` 抽头实测 RMS/峰值 —— 这是 S1 最硬的那块证据。

**S1 顺带证实的一件事**：B 站 SPA 切视频**复用同一个 `<video>` 元素**。这直接解释了「切视频后永久断哑」的成因 —— 对一个被复用的元素调 `source.disconnect()`，等于把正在播的视频永久断哑。本方案「永不 disconnect」的设计在这个场景下天然正确。

> 但同一个事实在 S2.1 变成了**另一个 bug 的成因**：元素被复用意味着
> `tick()` 里「元素被替换才触发分析」的条件永远不成立 → 换视频后脚本什么都不做。
> 补法是额外比对完整 `location.href`（见 S2.1 第 4 层修复）。

## S0 关键实测结论（详见主文档 §2.7）

1. **B 站「音量均衡」= Web Audio `createMediaElementSource` + `GainNode`**，增益值直接用响度元数据算（实测 `20·log10(3.0903)=9.80dB` vs 元数据公式 `9.9dB`，吻合 0.1dB）

### 端到端验证怎么跑

```bash
# 1. 复制本机 Edge 登录态到独立 profile（不动用户正在用的浏览器）
DEST=/tmp/bl_edge_profile
mkdir -p "$DEST/Default"
S="$HOME/Library/Application Support/Microsoft Edge"
cp "$S/Local State" "$DEST/"; cp "$S/Default/Preferences" "$S/Default/Cookies" "$DEST/Default/"
cp -R "$S/Default/Local Storage" "$S/Default/Session Storage" "$DEST/Default/"

# 2. 起 headless 实例
"/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge" \
  --headless=new --no-sandbox --remote-debugging-port=9222 --user-data-dir="$DEST" \
  --no-first-run --no-default-browser-check --disable-gpu \
  --autoplay-policy=no-user-gesture-required about:blank &

# 3. 跑
node build.mjs
node probe/s2-unit.mjs                     # 105 项（S2 + S2.2 + S3.2.5 限幅文案）
```
